# On1xMETA processor

`On1xMETA.llsynth` is a LibStone LLSynth language specification for `.o1m`
processor rules. LLSynth emits the actual DFA lexer and LR parser.
`generate.py` consumes that parser's tree, validates the declarations, and
emits immutable C++ pattern/replacement and semantic-constraint tables.
The canonical On1x parser continues to parse On1x programs.

The default compiler build compiles `canonicalize.o1m`, `desugar.o1m`, and
`semantic.o1m`; the normal frontend consumes those tables. Generated programs
and compiler rule execution require neither Python nor Perl.

The optional [typed partial evaluator](PARTIAL_EVALUATION.md) is independent
of the authored structural rule tables. Enable it with `--enable-opt partial-eval`.
The [Novostone HIR pass](../README.md#novostone) can also fold closed checked
expressions before the authored rules. Its report is available with
`--enable-opt novostone-hir --dump-processor`.
The [Firestone pass](../README.md#firestone) can expose additional `i64`
rewrites before the authored rules, including full-width constant arithmetic.

## Canonicalization requests in lowered MIR

MIR lowering preserves the legacy `canonicalized` and `fold-identity`
records for completed HIR rewrites. It separately looks for canonicalization
candidates left in lowered MIR, such as complementary boolean operands, a
strict i64 bound comparison, double checked negation, or a comparison against
i64 zero. The function-scoped `meta-canonical` requests select `mir-c11` and
`mir-archon` for the exact `x86_64-unknown-linux-gnu` target, and `mir-vm` with
a wildcard target. Safe and speculative requests are separate records; a
speculative request requires host opt-in and never substitutes for a proof
such as nonzero evidence. No host target is inferred at lowering time.

## Authoring

Each module starts with the same version and runtime budgets:

```text
meta 1;
budget steps 8388608 nodes 262144 depth 520;

rule lazy_and phase desugar priority 200
match Binary("&&", $left, $right)
replace Select($left, $right, Boolean("false"))
guard boolean;

constraint binary_arity phase semantic
match Binary require arity "2" message "binary expression needs two operands";
```

`#` starts a line comment. Rules declare `canonicalize` or `desugar`; constraints
declare `semantic`. Pattern constructors are `Unary`, `Binary`, `Boolean`,
`Integer`, and `Unit`; `$name` is a capture. Replacement-only `Select` constructs
lazy conditional evaluation. Operator/literal text is a quoted string. Select
and Unit have empty text; `Select("", ...)` is also accepted.

Guards apply to captured expression types: `boolean` and `integer` (exact i64).
`always` is limited to capture-free Boolean rules. `pure` is reserved and rejected
because purity alone cannot establish operand types. Rules cannot supply trusted
type, binding, ownership, effect or source-location evidence.

See `INTERFACE.md` and `include/on1x/meta_schema.hpp` for the flat C++ schema and
semantic property vocabulary. Semantic constraints only reject inconsistent
trees; they cannot manufacture annotations or replace the ordinary checker.

## Validation and determinism

* Boolean rewrites exhaustively preserve both result and lazy capture-evaluation
  trace, with at most six captures. Captures must be unique and used exactly once.
* Checked-i64 rewrites use a restrictive identity normal form: neutral zero/one
  arithmetic and total-order comparison duals. Floating-point and
  overflow-changing algebraic transformations are rejected.
* Every rewrite strictly decreases a natural-number weighted tree measure.
  Logical sugar has weight 100, `!=/<=/>=` weight 10, other nodes weight 1.
  This allows useful finite desugaring expansion.
* Equal-priority overlapping patterns are rejected. Ordering is phase, descending
  priority, then name. Names are globally unique. Input order and absolute
  checkout paths do not affect generated bytes.
* Generation is limited to 64 modules, 256 KiB per module, 512 declarations,
  128 nodes per pattern/replacement and depth 32. Runtime budget declarations
  have explicit upper bounds (16,777,216 steps, 2,000,000 nodes, depth 1024).
* Diagnostics retain `.o1m` basename, line and column; generated replacement
  nodes inherit the matched On1x location and captures retain their identities.
  Output is published only after complete parse/validation.

## Build, bootstrap, and regeneration

When Perl and configured LibStone are available, CMake regenerates the Python
parser from `On1xMETA.llsynth`. Otherwise it verifies and uses
`generated/On1xMETA.py`, which is actual unmodified LLSynth output.
`parser_manifest.json` pins grammar, parser and all seven generator source files.
The bootstrap gate fails for stale grammar/parser or a mismatched available
LibStone generator. Python 3 remains a build-time prerequisite.

```sh
cmake --build BUILD --target on1x_meta_tables
cmake --build BUILD --target on1x_meta_check
cmake --build BUILD --target on1x_meta_regenerate
ctest --test-dir BUILD -R '^on1x.processor.' --output-on-failure
```

`on1x_meta_regenerate` intentionally refreshes checked snapshots after authored
changes; `on1x_meta_check` independently regenerates and compares all artifacts.
All generator module and `.o1m` dependencies are explicit CMake dependencies.
`ON1X_META_RULE_FILES` can select alternate validated rule modules.
Existing CMake caches using the former default module paths migrate automatically.
Custom selections are not modified; update any paths that reference moved
shipping modules.

Standalone generation:

```sh
perl on1x/third_party/libstone/cornerstone/LLSynth/scripts/llsynth.pl \
  --mode=interpret -T python3 -o BUILD/On1xMETA.py \
  on1x/hir/On1xMETA/On1xMETA.llsynth
python3 -B on1x/hir/On1xMETA/generate.py --parser BUILD/On1xMETA.py \
  --output BUILD/on1x_meta_rules.hpp --manifest BUILD/rules_manifest.json \
  on1x/hir/On1xMETA/canonicalize.o1m on1x/hir/On1xMETA/desugar.o1m \
  on1x/hir/On1xMETA/semantic.o1m
```

The generator tests regenerate with real LLSynth twice, compile and inspect
the resulting C++ tables, check relocated/shuffled-input determinism and reject
malformed/unsafe/budget-exhausting declarations. Three compiler test executables
compile production processor implementations against independently authored
add-zero/subtract-zero/forbid-integer fixtures, demonstrating that `.o1m` payload
changes control checked HIR and semantic rejection. The rewrite fixtures
preserve evaluation. An isolated build regression places a stale same-named
header in the parent's binary directory and verifies that the production CMake
selects the real generated tables without deleting the stale artifact.
