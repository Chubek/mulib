# Compiled canonicalization and desugaring rules

This page describes the **checked** rules. Intrinsic source operators are
handled earlier by the [mandatory source program](README.md#mandatory-source-operator-program).

`canonicalize.o1m` and `desugar.o1m` are executable compiler inputs. The
LLSynth-generated On1xMETA parser and `generate.py` compile their structural
match/replacement trees into `on1x_meta_rules.hpp`. `hir/On1xMETA/processor.cpp` interprets
those immutable trees against the existing `Unit`, `Expr` and `Stmt`; rule names
are reporting labels, never C++ pass selectors.

## Supported rules

| Phase | Operation | Restriction |
|---|---|---|
| Desugar | `true && a`, `a && true`, `false || a`, `a || false` → `a` | checked booleans; the omitted operand is a neutral literal |
| Desugar | `false && false` → `false`; `true || true` → `true` | closed literals only; does not delete a captured call |
| Desugar | `a && b` → `Select(a,b,false)` | checked booleans |
| Desugar | `a || b` → `Select(a,true,b)` | checked booleans |
| Desugar | `a != b` → `!(a == b)` | checked i64 or booleans |
| Desugar | `a <= b` → `!(a > b)`; `a >= b` → `!(a < b)` | checked i64 only |
| Canonicalize | `!!a` → `a`; `!true` → `false`; `!false` → `true` | checked booleans |
| Canonicalize | `a == true`, `true == a` → `a` | checked booleans |
| Canonicalize | `a == false`, `false == a` → `!a` | checked booleans |
| Canonicalize | `(!a) == (!b)` → `a == b` | checked booleans |
| Canonicalize | `(!a) != b`, `a != (!b)` → `a == b` | checked booleans, after `!=` desugaring |
| Canonicalize | `a + 0`, `0 + a`, `a - 0` → `a` | checked i64 only |
| Canonicalize | `-0` → `0` | unary minus on the exact i64 literal zero; exposes neutral operands such as `a + -0` |
| Canonicalize | `a * 1`, `1 * a`, `a / 1` → `a` | checked i64 only |

`Select` is a replacement constructor, not a source or HIR node. It constructs
an ordinary bool `Region`, a `Storage` result slot, an `If` with one
`Initialize` in each branch, and a local result expression. The condition is
evaluated once and only the selected branch executes. Existing C11 and MIR
lowerers consume those canonical nodes.

For the neutral `&&` / `||` cases, the specialized desugar rules run before
the general `Select` replacements, so no branch or result slot is needed.
Canonicalization exposes neutral literals such as `!false` before this step;
`!=` desugaring can in turn expose negated equality for canonicalization.
Equality remains eager: even if `a` returns false, `b` still runs; if `a`
traps, `b` does not run.

Float arithmetic and comparisons are deliberately outside these rules: signed
zero and NaN invalidate several integer identities. No zero-multiplication,
self-subtraction, self-division, double arithmetic negation, dead-branch
elimination, general constant checked arithmetic, effect duplication or arbitrary
statement deletion is implemented.

## Authority, effects and provenance

The pipeline must first run ordinary source typing and the complete mandatory
canonical/ownership verification. An invalid operand remains an error even if
it sits in a runtime-unselected branch. These rules never grant type, ownership,
foreign-call, unsafe-region or concurrency authority. The caller rechecks the
transformed tree with the ordinary checker and canonical verifiers.

Each capture is moved exactly once, rather than copied or reconstructed.
Operators may disappear only where their checked operation cannot trap; operand
calls, traps and owner effects remain. Comparisons preserve left-to-right
operand order. Boolean desugaring preserves conditional evaluation.

Captured subtrees retain their source locations, syntax contexts, lexical
references, types and other checked metadata. Constructed nodes receive the
matched operator's source location; they do not impersonate captured source
expressions. Fresh `@processor_N` names are unlexable in source and are checked
against existing function, parameter, local, pattern, capture and expression
names, including names generated by previous canonical passes.

Generic prototypes, template statements, universality proofs and retained
declaration evidence are not rewrite targets. Whole-unit transactional cloning
preserves them.

## Determinism and resource bounds

The generated rule order is phase, descending priority, then stable name.
Traversal is deterministic postorder, normalizing replacements to a fixed point.
Budgets are bounded by both the generated program's limits and the caller's
`processor::Limits`: nodes, work steps, depth and rewrite applications. Inventory
visits patterns, macro trees, proof trees and generic instances before recursive
cloning. Fresh-name allocation is deterministic.

`processor::apply` works on a private clone. Budget or construction failure
leaves the caller's `Unit` intact. Resource exhaustion raises a located
`ON1X-PROCESSOR-LIMIT`; malformed compiled construction raises
`ON1X-PROCESSOR`. The caller is responsible for checking the resulting candidate
before publishing compiler output.

A successful canonicalization records a `canonicalized` hint for its emitted
function in MIR v4. A replacement that is exactly one captured operand
records both that hint and a `fold-identity` request, including for a desugar
rule. For a redex with operands, exported evidence requires distinct source
locations for the operator and at least one operand; this excludes synthetic guards used by
ordinary control lowering. Non-identity desugaring does not alone upgrade the
format either. The producer records structural rule results, not source names
or zero-hit rules. The request is advisory: a consumer must establish any
further identity fold against its own IR.

`tests/test_processor_engine.cpp` checks actual generated rule application,
fixed-point idempotence, source/context preservation, private-name collision
avoidance, canonical value/control verification of Select expansion, negative
float/zero laws, prototype preservation and transactional work/node/depth/rewrite
exhaustion, including failure after a successful internal rewrite. End-to-end
source/C11/native coverage is in `tests/test_processor.py`.
`tests/test_processor_predicates.py` checks individual negated-equality rule
hits, compares complete direct and MIR-generated C11 with explicit `a == b`,
and exercises both operand trap positions plus all four input pairs through
direct C11 and the MIR evaluator. It also checks that `mark(x) + -0` emits the
same direct and MIR-generated C11 as `mark(x)` at both signed integer limits,
that negation overflow still reports after `mark` runs, and that negative
floating-point zeros retain their sign.
