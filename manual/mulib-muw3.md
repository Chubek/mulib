# MuW3 HTTP client

[Manuals](README.md) · [Weblet engine](mulib-muw3-mune.md)

**Header:** `include/mulib-muw3.h` · **Switch:** `MULIB_IMPL_MUW3`

MuW3 composes MuLIB's HTTP parser, webclient and verified HTTPS adapter into a
synchronous client with bounded redirects, native TCP/DNS transport, binary bodies
and form/query encoding. A client is a value configuration with borrowed callback
contexts; separate clients can run independently. It has no process-global state.

## Build and ownership

Define `MULIB_IMPL_MUW3`, `HTTPS`, `TSL`, `WEBCLIENT`, `HTTP`, `URI`, `INET4`,
`INET6`, `PARSEC`, `BUFFER`, `STRBUF`, and `SOCKET` implementation switches before
including the header in one TU. Each short name means `MULIB_IMPL_<NAME>`.
Also select `TLS`, `ENTROPY`, `SHA`, `HKDF`, `X25519`, `AES_GCM`, `DER`,
`SIGNATURE`, `X509`, and `BASE64`. The convenience header
`detail/mulib-tls-implementation.h` selects this cryptographic closure explicitly.
No public module switch enables another implicitly. For native hostname resolution, define
`_POSIX_C_SOURCE=200809L` before all system headers. See
[`examples/modules/muw3.c`](../examples/modules/muw3.c) for an offline transport.

```c
mulib_muw3_client_t client = mulib_muw3_client_default();
mulib_muw3_request_t request = {0};
mulib_muw3_response_t response = {0};
request.url = "http://localhost:8000/data";
if (mulib_muw3_perform(&client, &request, &response) == MULIB_MUW3_OK) {
    /* response.message.body is binary; use body_length, not strlen. */
    mulib_muw3_response_free(&response);
}
```

Requests and callback contexts are borrowed for the call. A NULL method is GET.
The response owns its message, trailers and final URL. Success may include any
HTTP status, including 4xx/5xx. Failure leaves the output unchanged; it must not
already own a response on success. `response_free` accepts NULL/zero/repeated free.
Do not mutate a client from its transport callback.

Results: OK=1, INVALID=-1, LIMIT=-2, NOMEM=-3, TRANSPORT=-4,
TLS_REQUIRED=-5 (retained for source compatibility), REDIRECT=-6.
Native TLS failures return TRANSPORT. `mulib_muw3_strerror` returns static text.

## Redirects and limits

`client_default` selects five redirects, 8192 URL bytes, 30-second socket waits,
and `MULIB_HTTP_CHUNK_METADATA`. Zero byte/time limits select defaults; **zero
max_redirects disables following**. The redirect cap cannot exceed 100; URL limits
cannot exceed 1 MiB. HTTP defaults are 32 KiB headers, 100 fields, 16 MiB decoded
body and 32 MiB raw response per hop, adjustable through `options.web`.

* Follow 301/302/303/307/308 when Location is present; resolve relative references
  using MuLIB URI resolution. Strip fragments before transmission. Reject URL
  userinfo, unsupported schemes and invalid/zero ports.
* 301/302 rewrite POST to GET. 303 rewrites every method except HEAD to GET.
  Rewrites drop the body and content/framing headers. 307/308 preserve method/body.
* Origin changes remove Authorization, Proxy-Authorization and Cookie. Custom
  credential headers remain application-controlled. Cross-origin removal persists
  across the remainder of the redirect chain.
* HTTPS-to-HTTP redirects fail unless `allow_downgrade=1`. Loops terminate at the
  redirect cap. A redirect without Location remains an ordinary response.
* Host/Connection are generated by webclient; overriding them is invalid. Bodies
  with Transfer-Encoding: chunked are serialized as decoded binary content.

`mulib_muw3_form(fields,count,limit,&text)` encodes copied output from borrowed
name/value pairs. Space becomes `+`; delimiters/UTF-8 bytes are percent-encoded.
Zero limit selects 1 MiB. Output is malloc-owned, unchanged on error. It can be
appended after `?` for a query. Input fields are NUL-terminated strings.

## Transport and current protocol scope

With `client.http=NULL`, POSIX sockets use system DNS, IPv4/IPv6, short-write loops,
close-on-exec descriptors and a fresh connection per hop. System DNS has its own
timeout policy; socket connect attempts and I/O waits each use `timeout_ms` (not
a whole-request deadline). Native transport sends Connection: close and reads
through EOF. A peer that ignores connection-close may time out. Unsupported
platforms/feature profiles report transport failure rather than pretending to send.

A custom `http` callback follows the webclient contract: send the complete request,
feed response chunks, return 1 after EOF, and stop if the receive sink returns 0.
`http_user` is passed unchanged. The sink enforces raw response bounds.

HTTPS defaults to [MuLIB TLS 1.3](mulib-tls.md): X25519, AES-128-GCM,
SHA-256/HKDF, certificate-chain/SAN verification and authenticated shutdown.
`options.ca_file` selects a PEM trust bundle; NULL uses system trust.
`options.trust` borrows a preloaded `mulib_x509_store_t` and overrides the file.
These pointers must remain valid throughout the call (or the lifetime of an
engine that copies the client). An invalid explicit bundle fails without a
system-trust fallback. Custom `client.tls`/`tls_user` connectors still override
the native implementation and own verification and authenticated shutdown.

HTTP/1.1 framing, HEAD, informational responses, chunk metadata and EOF bodies
are supported. HTTP/2/3 headers remain standalone wire utilities; protocol
negotiation, HTTP/1.0, decompression, proxy tunneling, multipart construction,
connection pooling and a cookie jar are not provided by this client version.
Set-Cookie duplicates can be read with `mulib_http_header_next`; application code
can maintain cookie/authentication state explicitly.

## Incremental response API

`mulib_muw3_stream(client, request, callback, user, response)` streams decoded
body bytes live over the same native/custom HTTP and verified TLS transports.
The `mulib_http_body_fn` callback sees final headers once with NULL/0 and then
body slices. Return 1 to continue; 0 aborts with INVALID. This API does not follow
redirects, regardless of `max_redirects`. Every HTTP status is delivered normally.
Successful output owns the URL, headers and trailers, with an empty body. Byte
limits are cumulative; body bytes are not retained. Output is unchanged on error,
although callbacks may already have run. The final result still requires
successful transport EOF/TLS authenticated shutdown. The buffered `perform` API
keeps its existing behavior. The [OpenAI client](mulib-openai-client.md) builds
live JSON/SSE events and explicit cancellation results on this API.

## Command-line host

`make muw3` builds `build/muw3` and `build/microchand`. CMake builds `lmuw3`,
`mulib_microchan`, `muw3` and `microchand` with `MULIB_BUILD_MUW3=ON` (default).

```
muw3 [-X METHOD] [-H 'Name: value'] [-d DATA] [-i] [-o FILE]
     [--redirects N] [--timeout MS] [--cacert PEM] URL
muw3 [--cacert PEM] --weblet FILE [ARGS...]
```

`-d` defaults the method to POST; `-H` repeats. `-i` prints received headers before
the decoded body (diagnostic output, not a reserialized chunked message).
`-o` writes only after a successful transaction. HTTP error statuses do not change
the exit code; protocol/transport/I/O errors exit 1, usage errors 2. Both HTTP and
HTTPS are supported. Example: `build/muw3 --cacert roots.pem https://localhost:8443/`.
For C embedding see [`examples/muw3-https.c`](../examples/muw3-https.c).

Verification: `make check-muw3`, `tests/test_http_hardening.c`, and
`tests/test_http_alloc.c`. `make check-tls` adds loopback HTTPS interoperability,
certificate and TLS failure checks, and cryptographic vectors.
