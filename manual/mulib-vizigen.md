# mulib-vizigen

[Manuals](README.md) · [Library index](index.md)

Compile Zephyr ASDL schemas with named semantic actions into portable event
dispatch bytecode. The same executor serves parser-time push listeners and an
AST visitor walker. No native code, C snippets or process addresses are stored.

## Integration

Define `MULIB_IMPL_VIZIGEN` once, plus these transitive implementation switches:

```
MULIB_IMPL_ASDL MULIB_IMPL_ARENA MULIB_IMPL_PARSEC MULIB_IMPL_STRBUF
MULIB_IMPL_BINFILE MULIB_IMPL_BINFILEREADER MULIB_IMPL_BINFILEWRITER
MULIB_IMPL_BYCUTILS MULIB_IMPL_BUFFER MULIB_IMPL_WALKER MULIB_IMPL_EVTSTREAM
MULIB_IMPL_EVTLISTENER
```

Include `mulib-vizigen.h`. AST allocation is optional; define `MULIB_IMPL_AST`
when using its constructors, and `MULIB_IMPL_MMFILE` when opening mappings.
Neither implementation switch is needed just to execute bytecode. See the
runnable `examples/modules/vizigen.c` and focused `tests/test_vizigen.c`.

## Grammar and action semantics

Every schema accepted by `mulib-asdl.h` is accepted unchanged, including bare
descriptions, module wrappers, comments, products, recursive sums, unnamed
fields, optional/sequence fields and shared attributes. The existing ASDL
parser and semantic validator are reused, not replaced by a second schema
parser. The only extension is an action suffix:

```asdl
module Trees {
  expr = Num(int value) @enter(number) @leave(finish)
       | Add(expr left, expr right) @leave(add)
       | Empty
       attributes (int? line)
  document = (expr* body) @leave(document)
}
```

`@enter(name)` runs before a node's children; `@leave(name)` runs after them.
Annotations must follow the complete product or constructor, before the next
`|`, `attributes`, declaration or closing module brace. They cannot annotate
fields, shared attributes, modules or sum types as a whole. Each production
allows at most one annotation of each kind, in either order. The annotation
spelling has no internal whitespace; names begin with an ASCII letter and
contain letters, digits or underscores (maximum 255 bytes). Comments may
separate annotations and annotations in comments are ignored. Unknown
annotations, malformed suffixes and embedded C blocks are errors.

Products dispatch by their type name (`document`), sums by constructor name
(`Num`, `Add`, `Empty`). Annotations are optional: unannotated productions have
no callback. No wildcard or implicit action is inserted. As in ASDL, names are
case-sensitive. `mulib_vizigen_generate` provides the same facility using a
validated ASDL module and an array of `mulib_vizigen_rule_t` instead of source
annotations; it rejects unknown productions and duplicate production/kind
pairs.

`mulib_vizigen_compile` uses `mulib_asdl_options_t` for parser settings and the
default module name; textual output format and C prefix are irrelevant. Both
compilers return 1 on success and 0 on failure, append atomically to a MuLIB
binary buffer and accept source/rules that alias the destination's existing
bytes. Errors use `mulib_asdl_error_t`; syntax positions are byte offsets and
one-based coordinates in the original annotated source. API generation and
duplicate-rule diagnostics may have a zero span. Inputs are not retained.

## Execution and parser-time event streams

Open the generated bytes with `mulib_vizigen_open`, then bind a table of
`mulib_vizigen_action_t` using `mulib_vizigen_runtime_init`. Initialization
validates the bytecode and resolves **all** referenced names before any
callback can run. Missing bindings, duplicate binding names and NULL callbacks
fail initialization; unused bindings are allowed. Failure leaves the runtime
unchanged. Program bytes, binding names and the table are borrowed and must
remain immutable and alive throughout execution. Runtime objects require
successful initialization; do not construct them by filling individual fields.

Callbacks receive the complete `mulib_event_t`, including kind, depth and a
borrowed node (production, binary-safe text, source offset and optional action
metadata). Return 1 to continue, 0 to stop, or -1 on error. Positive callback
values normalize to 1 and negative values to -1. No node is retained. Host
callbacks may use their own user state, but may not mutate the traversed tree,
runtime, bindings or bytecode during execution. Concurrent executions require
appropriate synchronization for shared callback state.

* `mulib_vizigen_walk(&runtime, root)` walks an AST/subtree with balanced
  enter/leave events using `mulib-walker.h`. NULL root is empty. Subtrees start
  at depth zero. There is no allocation during walking or dispatch.
* `mulib_vizigen_listener(&runtime)` creates a `mulib_evtlistener_t` from
  `mulib-evtlistener.h`.
  An incremental file parser delivers committed events with
  `mulib_evtlistener_push(&listener, &event)` as input is consumed. The parser
  may provide a temporary, stack-local `mulib_ast_t` containing only production,
  text, length and offset; tree links can be NULL. Node/text lifetime need only
  cover the call. `mulib_vizigen_dispatch` also accepts events directly.
* `mulib_evtlistener_listen` routes an existing pull stream through that same
  listener. All three paths execute exactly the same bytecode.

Execution returns 1 for completion/continue, 0 for callback cancellation and
-1 for an invalid event or callback error. Unmatched productions are ignored.
The runtime has no traversal cursor and can be reused without resetting it.
Stopped walks may have unmatched ENTER events; no synthetic LEAVEs or rollback
are performed. A stopped pull stream has already consumed the delivered event.

This is an **action dispatch compiler**, not a concrete-syntax parser generator
or an ASDL instance validator. Field cardinality/types are schema-validated at
compile time, not enforced against event payloads. Adapters for formats such
as XAS/XtAS supply their own parsing and node/field interpretation. Push
producers are responsible for balancing/depth and must not emit speculative
backtracking events unless callbacks are designed for that. Bytecode describes
semantic dispatch only; it does not serialize the ASDL schema or an AST.

## Binary persistence and memory mapping

The version-1 format is little-endian and has no alignment requirements:

| Field | Encoding |
| --- | --- |
| Magic | Four bytes `VIZI` |
| Version | u32, value 1 |
| Total length | u32, includes the 16-byte header |
| Instruction count | u32 |
| Each instruction | u32 event opcode (0 ENTER, 1 LEAVE), u32 production byte count, u32 action byte count, production bytes, action bytes |

Both strings include one terminal NUL, have 1–255 identifier bytes and no
embedded NULs. Each instruction means `MATCH production/kind; CALL action`.
Instructions execute in file order. The source/API generator rejects duplicate
production/kind pairs; structurally valid externally produced bytecode may
contain repeated instructions. There are no jumps, pointers or executable
machine code. Unknown versions/opcodes, invalid names, inconsistent lengths,
truncation and trailing bytes are rejected by `mulib_vizigen_open` before use.
Programs are trusted to remain unchanged after validation.

`mulib_vizigen_serialize` atomically appends the validated binary representation
unchanged to `mulib_buffer_t`. Write that buffer with the application's usual
file I/O. `mulib_vizigen_deserialize` consumes one framed program at a
`mulib_binfilereader_t` cursor, borrowing the underlying bytes; both reader and
output remain unchanged on failure. Multiple programs may share a container.
This uses `mulib-binfilereader.h` / `mulib-binfilewriter.h` for decoding and
encoding, not native struct dumps.

For zero-copy loading:

```c
mulib_mmfile_t mapping = MULIB_MMFILE_INIT;
mulib_vizigen_program_t program;
/* Check each result in production code. */
if (mulib_mmfile_open(&mapping, "actions.bin", 0) == MULIB_MMFILE_OK) {
    if (mulib_vizigen_from_mapping(&program, &mapping)) {
        /* Bind callbacks, then execute while mapping remains active. */
    }
    mulib_mmfile_close(&mapping);
}
```

No copying, relocation or heap allocation is required to open mapped bytecode.
Alternatively call `mulib_vizigen_open` with any immutable mapped byte span.
Do not truncate or modify the underlying file while it is mapped. Mapping
availability/platform errors follow `mulib-mmfile.h` (POSIX with explicit
unsupported fallback).

## Limits and ownership

Source is limited to 16 MiB; ASDL/parsec limits also apply. Annotations,
instructions and bindings are each limited to 65,536. Compilation and binding
each allow at most 1,000,000 comparison/work units per phase, rejecting
pathological inputs with a limit error (or failed binding). Bytecode loading
accepts at most 64 MiB and performs a linear structural validation pass.
Dispatch scans the instructions and matches host bindings; large hot-path
tables may benefit from application-side sharding. All byte arithmetic uses
bounds-checked MuLIB binary readers; unaligned input is supported.

Generated buffers are owned by the caller (`mulib_buffer_free`). Programs,
deserialized views, listeners and runtimes own no memory and need no destroy
function. Reallocating/freeing a buffer or closing its mapping invalidates all
views/runtimes that reference it. The compiler stages output so failures,
including allocation failures, do not alter the destination.
